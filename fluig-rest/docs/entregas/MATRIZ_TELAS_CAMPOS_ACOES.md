# Matriz tela → campo/ação → procedure → API → arquivo

Atualizada em 2026-09-21 — sincronização visual do mockup aprovado. Fonte: cobertura-telas.json. Os contratos permanecem no catálogo; esta matriz não cria backend.

Protótipo: [abrir as quatro áreas](mockups/index.html). Datas oficiais: [Planner da gestão](CRONOGRAMA_PLANNER_GESTAO.md).

**Organização visual:** Embalagens possui as abas Tipos de Embalagem e Itens Controlados. Bags possui Manutenção de Bags e Consulta de Bags. As abas organizam a experiência e não representam APIs, procedures ou serviços independentes. Manutenção de Etiquetas permanece uma área própria; Monitor de Documentos de Recebimento é uma área independente, ainda sem contrato funcional liberado.

**Padrão visual:** filtros no topo; Buscar/Limpar; Novo abre modal; Editar e demais ações ficam na linha; Ativo/Inativo usa toggle na linha. Ações em lote usam checkbox e comando acima da grid.

**Autocomplete:** Estabelecimento, Item e Tipo de Embalagem usam um único campo físico por entidade. O usuário digita código ou descrição; o match código OU descrição ocorre no Progress; o Fluig apresenta código + descrição e envia o código selecionado. Mantêm-se mínimo de 2 caracteres, espera de 350 ms, máximo 20, cursor, cancelamento e descarte de respostas antigas.

**Bag:** “Pesquisar dentro desta Bag” filtra localmente o conteúdo já carregado. Buscar elegíveis, inserir e remover permanecem operações próprias do contexto da Bag e conservam o estado real de seus contratos.

**Leitura:** LOCAL não chama servidor. Item marcado como proposta, necessidade ou rota não contratada continua pendente. Esta revisão visual não altera API, procedure Progress, BO, modelo de dados ou regra de negócio.

## Como entregar e manter

1. Navegar nas quatro áreas e nas abas internas. Dados e ações do mockup são demonstrações locais; nenhuma chamada real ou gravação é executada.
2. Usar o ID da matriz para registrar dúvida, teste ou implementação. Abas e modais não ganham backend próprio por existirem visualmente.
3. Preservar ações por linha, modais, toggles e o padrão de seleção em lote.
4. Para cada pendência, fechar o contrato antes de implementar fonte, rota ou integração.
5. Testar sucesso, vazio, erro, repetição, autorização, paginação, concorrência e respostas fora de ordem conforme a natureza de cada operação.
